## ② `slidesPersonal`(본진) vs `slidesVariants`(첫걸음) — 메커니즘 비대칭 평가

### 구조 비교

| 항목 | 본진 `slidesPersonal` | 첫걸음 `slidesVariants` |
|---|---|---|
| 오버라이드 단위 | 강의 전체 덱을 통째로 교체(all-or-nothing) | 슬라이드 **인덱스 단위** 부분 오버라이드(`overrideMap[i] \|\| baseSlide`) |
| 스위치 | `?variant=personal` 하나뿐, 강사 1인칭 경험담 전용 | `?variant=<페르소나키>`, `SITE_CONFIG.personas`에 등록된 키만큼 무제한 확장 가능 |
| 현재 등록 수 | 1개(고정, 레지스트리 없음 — 하드코딩된 예약어) | 3개 등록(`default`/`student`/`owner`), 실제 오버라이드는 01강 1건(파일럿)뿐 |
| 엔진 소비 지점 | `js/slides.js:152`에서 `window.__variantPersonal` 직접 참조(강 단위 if 분기, 함수화 안 됨) | `js/main.js:39-44`의 `App.resolveSlides(lecture)` 단일 함수로 정규화, `slides.js`·`tocKeyLines` 등 여러 소비처가 공유 |
| 데이터 형태 | `lecture.slidesPersonal = [slide0, slide1, ...]`(완전한 배열) | `lecture.slidesVariants = { personaKey: { idx: slideObj, ... } }`(맵의 맵) |
| 문서화 | `docs/톤앤매너.md` §1(규격 분리)만 언급, 별도 작성 가이드 없음 | `docs/페르소나_작성_가이드.md` 전용 문서 — 개념·데이터구조·전환로직·명명관례·작성절차·**본진 이식 메모**까지 포함 |
| 하위 호환성 | — | **본진 슬라이드 배열을 한 글자도 안 건드리고** 오버라이드 가능(인덱스 방식 채택 이유가 명시적으로 이것) |

### 실제 코드 확인
- 본진 `js/main.js`에는 `App.resolveSlides` 자체가 **존재하지 않는다**(`window.App` 객체는 있으나 해당 메서드 없음, `grep` 결과 0건). `js/slides.js:152`가 `slides = (window.__variantPersonal && lecture.slidesPersonal) ? lecture.slidesPersonal : (lecture.slides || [])`로 강 렌더 시점에 직접 분기.
- 첫걸음 `js/main.js:39-44`는 이를 함수로 일반화하고, 기존 `slidesPersonal` 예약어 처리(`VARIANT_PERSONAL`)를 **그대로 흡수한 채** 페르소나 오버라이드 합성을 추가했다(`js/slides.js:152`도 `slides = window.App.resolveSlides(lecture)` 한 줄로 단순화됨). 즉 첫걸음의 구현은 본진 메커니즘을 대체한 게 아니라 **상위 호환으로 감싼 것** — 페르소나가 0개 등록된 상태에서 동작을 재현하면 본진과 동일하게 움직인다.
- `docs/페르소나_작성_가이드.md` "본진 이식 메모"는 이 사실을 이미 스스로 인지하고, 마이그레이션 경로 두 가지(① `slidesPersonal` → `slidesVariants.personal = {전체 인덱스}`로 변환 ② `personal` 예약어를 유지한 채 합성 로직만 공유)까지 구체적으로 제시해뒀다.

### 마이그레이션 필요성에 대한 의견 — **애매(조건부)**

**이식 쪽에 힘을 싣는 근거**:
- `js/main.js`/`js/slides.js`는 §1 공유 엔진 파일인데, 두 저장소의 실제 구현이 이미 구조적으로 갈라져 있다(본진은 인라인 if, 첫걸음은 함수화+레지스트리). §1 원칙("함부로 갈라치지 않는다")에 비춰보면 방치할수록 두 파일의 diff가 벌어져 향후 다른 버그 픽스(§5 이식 절차)의 patch 충돌 가능성이 커진다.
- 첫걸음 쪽 구현은 스스로 "상위 호환"임을 설계·문서로 증명해뒀고(하위 호환 유지, 이식 경로 2가지 제시), `personas` 미등록 시 무동작이라 본진에 들여와도 즉시 회귀 위험은 낮다.

**보류 쪽에 힘을 싣는 근거**:
- 본진은 20강 콘텐츠가 "완료" 상태이고, 실제 persona 콘텐츠 수요가 0건이다(경험판 1건 외 페르소나 분화 요구 자체가 없음). YAGNI 관점에서 지금 엔진을 확장할 실익이 없다.
- `?variant=personal` 예약어 충돌 처리가 "그때 가서 결정"으로 남아 있어(가이드 문서 자신도 "실제 이식은 별도 지시서에서 결정"이라 명시), 단순 파일 복사로 끝나지 않는 설계 결정이 필요하다.
- 인덱스 기반 오버라이드는 가이드 문서 자체가 명시한 트레이드오프(기본판 슬라이드 삽입/삭제 시 인덱스 밀림)가 있다 — 본진처럼 이미 완결된 20강에 향후 슬라이드 추가/삭제(예: 오탈자 수정 중 슬라이드 1장 추가)가 생기면, 만약 그 강에 `slidesVariants`가 있었다면 조용히 엉뚱한 슬라이드를 오버라이드하는 사고가 날 수 있다. 지금 당장은 데이터가 0건이라 무해하지만, 이식 시점에 이 리스크를 얼마나 관리할지 결정이 필요하다.

**결론**: 지금 당장 이식할 필요성은 낮다(콘텐츠 수요 없음) — 다만 "언젠가 본진이 페르소나 콘텐츠를 만들 계획이 생기는 시점"에는 이식이 합리적 선택이다(백지에서 새 메커니즘을 또 만들 이유가 없고, 첫걸음이 이미 설계·문서·테스트 골격까지 만들어뒀으므로). 그 전까지는 지금처럼 "설계 밖 + 문서로 추적"이 적절한 상태라고 판단한다. 굳이 지금 시점에 이식을 강행할 이유는 없지만, **완전히 방치하기보다는 §7 이식 이력에 "대기 중(pending)" 항목으로 한 줄 등재해두는 것**을 권장한다(아래 문안 참고) — 그래야 다음에 첫걸음의 `main.js`/`slides.js`에 이 로직 관련 버그 픽스가 생겼을 때 "이건 이미 알려진 미이식 기능의 일부"임을 놓치지 않는다.
