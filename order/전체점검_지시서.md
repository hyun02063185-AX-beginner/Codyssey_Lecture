# CC 작업 지시서 — 플랫폼 전체 점검·수준 진단 보고

> 위치: `Last_Lecture/order/전체점검_지시서.md` · 경로는 프로젝트 루트 기준.
> **코드 수정 없음 — 점검·측정·보고만.** 결과는 보고서 파일로 남긴다.
> 대상: main(이론 플랫폼) + `feature/practice-room` 브랜치(진단실).

---

## 목적

이 강의 플랫폼의 현재 수준을 실측해 아래 6가지 질문에 **근거 있는 답**을 만든다.

1. 실제 강의로 하면 몇 분짜리인가?
2. 수강생 반복학습에 좋은 구조인가?
3. Lv 게이팅(레벨로 기능 해금)이 유효하게 설계돼 있나?
4. 진단실(브랜치)은 어떤 상태이고 무엇을 더 하면 되나?
5. 이 플랫폼을 DX로 볼 수 있나? (데이터가 쌓이는 구조인가)
6. AI를 적용한다면 어디가 좋은가? (기술적 준비 상태 포함)

---

## 산출물

`order/점검보고서_YYYYMMDD.md` 하나. 아래 각 파트의 측정 결과 + 마지막 종합 평가.
코드는 절대 수정하지 않는다(발견한 버그는 보고서에 기록만).

## 점검 절차

### 파트 0 · 환경

```bash
git branch --show-current            # 시작 전 현재 브랜치 기록
# main 점검: git checkout main → 서버 8000
# 브랜치 점검: git checkout feature/practice-room → 서버 8001
```
점검 후 원래 브랜치로 복귀. 두 서버를 동시에 띄워 비교해도 좋다.

### 파트 1 · 콘텐츠 실측 (질문 1의 근거)

`js/data.js`를 파싱해 표로:
- 강의별 슬라이드 수 / 타입 분포(cover·big·bullets·quote·split·closing·기타) / 총 슬라이드 수
- 강의별 총 글자 수(한글 기준) — 낭독·설명 시간 추정의 근거
- **소요시간 추정 계산**:
  - 자가 학습: 타입별 가중치(big·quote 10초, cover·closing 15초, bullets·split 40초)로 강당·전체 시간 산출
  - 강사 진행: 슬라이드당 발화 기준(big 30초, bullets/split 90초, 그 외 20초) + 강당 전환 1분으로 산출
  - 두 시나리오의 총합을 분 단위로 보고
- placeholder/빈 슬라이드 잔존 여부 (0이어야 함)

### 파트 2 · 전체 기능 QA (수준 파악)

main(8000)에서 전 동선 실행, 각 항목 ✅/⚠️/❌ + 메모:
- 인트로: 4테마 표시·선택·전체화면·클릭 입장, `prefers-reduced-motion` 동작
- 씬 전환: 인트로→워프→사유의 방→슬라이드→복귀 전 구간
- 상자 4개·카드 부채꼴·카드 선택(수정했던 클릭 안정성 재확인)
- 슬라이드: 20강 각각 진입해 첫·중간·끝 슬라이드 렌더 확인(전수), 키보드·버튼·스와이프 네비
- 스킨 5종: 각 스킨에서 시작화면+슬라이드 1개+HUD 대비 확인, 새로고침 유지
- 게이미피케이션: 발견 n/20·탐험도·완료점·DEMO 뱃지·초기화(↺)
- localStorage: 사용 중인 키 전체 목록화(키명·용도) — 파트 5의 근거
- 콘솔 에러·경고 수(브라우저 확장 제외)
- 반응형: 창 폭 375px(모바일 상당)에서 주요 화면 깨짐 여부

### 파트 3 · 반복학습 구조 감사 (질문 2)

기능 유무 체크 + 코드로 확인:
- [ ] 강의 중간 이탈 후 재진입 시 이어보기 되는가(아니면 처음부터인가)
- [ ] 특정 슬라이드로 직접 이동(딥링크/URL 해시) 가능한가
- [ ] 핵심만 훑는 수단(요약·핵심 모아보기)이 있는가
- [ ] 검색이 있는가
- [ ] 한 강 재열람에 걸리는 최소 클릭 수(입장→상자→카드→슬라이드 = 몇 번?)
→ "반복학습 관점 현재 점수 + 없는 것 목록"으로 정리.

### 파트 4 · Lv 게이팅 감사 (질문 3)

코드에서 실측:
- Lv 산정 공식(무엇으로 오르나), 현재 잠긴 기능 목록과 해금 조건
- 핵심 콘텐츠(이론 20강)가 잠겨 있지 않은지 확인
- 해금 조건이 화면에 **설명되는지**(수강생이 "뭘 해야 열리는지" 알 수 있나)
- 해금 순간 피드백(연출·알림) 유무
→ "게이팅 설계 평가: 잘된 점 / 빠진 점".

### 파트 5 · DX 판정 (질문 5)

- 쌓이는 데이터 전수 목록(파트 2의 localStorage 조사 활용): 진행도·열람·스킨·진단 응답·회고 등
- 각 데이터가 "쌓이기만 하는지 / 화면에 다시 쓰이는지" 분류
- 내보내기(복사·인쇄) 가능한 데이터는 무엇인지
→ "디지털화된 것 / 데이터화된 것 / 아직 아날로그(1회성)인 것" 3분류로 DX 수준 판정.

### 파트 6 · 진단실 상태 (질문 4) — 브랜치(8001)

- 현재 구현된 구역·스테이션 전수 목록(v3 유래·v4.1 검사실 포함 여부)
- 각 스테이션 동작 확인(입력→저장→산출물→새로고침 유지)
- 제안서/리포트: 포함 섹션·그래프 목록, 복사·인쇄 동작
- v4.1 지시서 대비 미구현 항목 목록
- main과의 충돌 가능성(같은 파일 수정 여부 — 병합 난이도 예측)

### 파트 7 · AI 적용 준비도 (질문 6)

수정 없이 **평가만**:
- RAG 조교 후보: data.js의 슬라이드 텍스트가 지식베이스로 추출 가능한 구조인가(강의·슬라이드 단위 식별자 유무)
- AI 처방전 후보: 진단 결과 데이터가 구조화돼 있어 프롬프트에 넣기 좋은 형태인가
- 관리 기능 후보: 수강 데이터가 개인 브라우저(localStorage)에만 있는 한계 명시 — 서버/수집 없이는 관리자 뷰 불가함을 기술적으로 확인
- Netlify Functions 도입 시 필요한 변경 규모 추정(파일 추가 수준인지, 구조 변경인지)

### 파트 8 · 종합 보고

보고서 마지막에:
1. **수준 한 줄 평가** (데모 수준 / 실사용 v1 / 상용 가능 중 어디쯤인지, 근거와 함께)
2. **질문 6개에 대한 실측 기반 답변** (각 3~5줄)
3. **발견된 버그·이슈 목록** (심각도 표기, 수정은 하지 않음)
4. **개선 우선순위 Top 5** (효과 대비 작업량 기준, 각 1줄 근거)
